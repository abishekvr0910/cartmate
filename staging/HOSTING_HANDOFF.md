## Engineering still required before invitations

### Tiny friend pilot: human age check is an option, not a bypass

The founder has no registered business, has mObywatel, and wants one real two-person friend test; the friend's mDowód availability is unknown. The integrated mObywatel age-only API is therefore **not available to CartMate today**. The official, free [mDowód QR verifier](https://weryfikator.mobywatel.gov.pl/verification-process) can be used by a human operator without building that API. It displays identity details transiently to the operator, so it is **not equivalent to an age-only assertion**. The [Ministry's QR guidance](https://www.gov.pl/web/cyfryzacja/kod-qr--skuteczna-metoda-weryfikacji-mdowodu) explains that live QR verification checks authenticity and age; merely having the mObywatel app is insufficient because [minors can use it](https://www.gov.pl/web/cyfryzacja/czy-osoby-ponizej-18-roku-zycia-moga-korzystac-z-aplikacji-mobywatel). A live, in-person government ID/passport inspection by the named operator is a possible fallback for a friend without mDowód, subject to the same privacy/safeguarding review. No screenshot, uploaded card, PESEL, document number, date of birth, or image is accepted by CartMate.

The backend now has an **off-by-default, staging-only** moderator attestation flow (`CARTMATE_MANUAL_AGE_PILOT_ENABLED=1`). It requires a single-use pilot invite, SMS-verified account, a five-minute one-use code generated from the subject's signed-in account, operator presence/consent/account-binding confirmations, and a moderator other than the subject. The age-blocked screen exposes the subject's account code and one-use code; an allowlisted moderator gets the check form there too. It records only method, operator, subject, time, decision and a seven-day expiry in an audit table; a moderator can revoke it and close the subject's sockets. Extra document fields are rejected. Production ignores this flag. This is a human trust process, **not** an automated or cryptographic CartMate-mObywatel integration. Before enabling it: name two verified adult moderators (each cannot approve themselves), agree who checks the friend, review the transient identity-data exposure and notice/appeal/retention with a qualified adviser, exercise negative and positive paths on the final host, and record the operator's check out of band. If any of these are absent, leave the flag at `0` and `/api/ready` blocked.

Sharing a GitHub repository link gives source code, not a working app. The current Capacitor config has neither an Android project nor a deployed API origin; an APK built from it would not run a real meetup. Host and prove the web pilot first, then decide whether an Android wrapper is worth the extra native security/QA work. A hosted HTTPS link works on Android and iPhone without installing an APK.

Hosting is **not** the only remaining engineering task. The tracked gaps in [`LAUNCH_READINESS.md`](../LAUNCH_READINESS.md) and [`NEXT_MODEL_EXECUTION_PLAN.md`](../NEXT_MODEL_EXECUTION_PLAN.md) include approving and exercising the operator method for this tiny staging pilot (or integrating a real signed age provider for broader rollout); browser session hardening (`localStorage` bearer token, 720-hour default, cookie/CSRF/rotation design); group closure/expiry and bounded chat/history; venue/scheduling truthfulness; account-rights and moderator incident operations; and manual accessibility/real-device fixes found by independent review. The optional Jev AI, native app, women-only mode, payments and Poland-wide meetups are **not** required for this closed pilot and should stay off rather than expand scope.
The Render rehearsal Blueprint now limits sessions to 24 hours, rather than relying on the backend's 720-hour default. This reduces the pilot's stolen-token window but does **not** solve the browser `localStorage` bearer-token design or replace a session/CSRF review.

With the manual route disabled, the deployed app should return `/api/ready` 503 and deny live discovery, chat and outings. Do not turn that guard off merely to obtain a green readiness response. If the reviewed human process is enabled for staging, readiness additionally requires two current 18+ moderator attestations; a 200 response is still **not** permission to invite people without the other release evidence.
